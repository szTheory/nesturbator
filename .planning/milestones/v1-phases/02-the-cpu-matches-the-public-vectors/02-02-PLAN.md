The library's `bus.c` lands in its final Phase 2 shape in the same commit that folds the CPU object into the library.

Purpose: CPU-01 tracer, second half. From here on every plan adds opcodes, data or the nightly to a pipeline that is proven end to end.
Output: `nesturbator_cpu` object library, `src/bus.c`, the vector program, `vectors_fixture.cmake`, `vecconv.a9` run through the CPU, and `bus.unit`.

2. `src/cpu.c` implements `nesturbator__cpu_step` as one `switch (opcode)` (Pattern 1, Claude's discretion). The only external calls are the two bus functions, one bus access per statement (D-08).
   - Add `static` helpers: `fetch` (read PC, then PC plus 1), a masked `set_flag(mask, cond)` that touches only its own bits, and `set_nz`, which sets N and Z through two `set_flag` calls. P is never rebuilt or normalised (Pitfall 1, D-16).

   - Add `case 0xA9` for LDA immediate.
   - Add a `default:` branch that runs the D-13 JAM sequence: 11 reads, PC ends at opcode address plus 1, `jammed = 1`. An opcode not yet written then stops the CPU visibly instead of doing something wrong. Plan 06 removes this branch once all 256 cases exist.
   - At the top of the step, while `jammed` is set, the step is one read of `0xFFFF` and returns.
   - Header comment: cite 64doc (nesdev.org/6502_cpu.txt) and NESdev Wiki "CPU unofficial opcodes" rev 23975.

   - decodes `0x0000`-`0x1FFF` to `bus.ram[addr & 0x7FF]` and returns `bus.open_bus` for every other read;
   - sets the latch to the value of every read and write;
   - ignores writes outside RAM.
   A comment cites NTSC M2 high for 15 of 24 ticks (NES-HARDWARE-CPU-APU, section 2 part 1, written in words).

   - With chunks 256 the file is a sample whose chunks run 00-ff, and only chunk `<opcode>` runs. With chunks 1 the file is that one opcode's chunk.
   - It reads every test through the reader, so the whole file is validated.
   - It uses one `static struct vector_machine` zeroed once and sets `nes.cpu.*` and the initial RAM pairs. It does not call `nesturbator_create` (D-11).
   - It calls `nesturbator__cpu_step` once, then compares pc, s, a, x, y, raw p, every final RAM pair, the cycle count and each cycle's addr, value and kind. A log overflow is a failure.
   - After each test it zeroes only the addresses in that test's initial and final lists.
   - For the first mismatch of a failing test it prints `<xx>.json[<index>]: <field> expected <e> got <g>` on stderr.
   - It ends with `65x02/<xx>: <failed> of <run> vectors failed` on stdout, and exits 1 if failed is not 0 or the reader reported an error (the reader's `offset <n>:` message goes to stderr). Stdout carries only that summary line; every other message goes to stderr. Tests run in file order, so the output is deterministic.
