## Why global chains and endpoint anchors remain insufficient

These are logical counterexamples, independent of any host or emulator implementation.

Let rendered frames 10,11 both be A and 12,13 both be B. Correct observations for an anchored start at 10 and two advances are A,A,B, with intended states 10,11,12. A dropped first advance followed by a doubled second advance produces actual states 10,10,12, also A,A,B. Both start and end anchors agree, and the globally compatible intended chain is unique once start 10 is fixed. Therefore neither a unique intended chain nor start/end anchors proves each command advanced exactly once.

An isolated dropped step from anchored frame10 produces A instead of intended frame11's A. An isolated doubled step from anchored frame11 produces frame13's B instead of intended frame12's B. Both pass a one-step screenshot assertion even though the initial state is exact. More later pictures can expose particular errors; that is not a proof that all checked commands discriminate.

For wrong-load evidence, frames10,11,12 all displaying A let a save at10 be mistakenly replaced by a valid state at11. A post-load advance displays frame12's A instead of intended frame11's A. ROM identity, state validity and successful load do not distinguish the two if the expected absolute save anchor was never retained. Longer chains may expose this example but cannot guarantee rejection for arbitrary repeated windows.

A global solver should constrain all branches to the same retained save origin and the rewind/run-ahead branches to their common second save. It should reject empty solutions and report ambiguity rather than invent certainty. Nevertheless, an existential correct-history solution only proves compatibility with observations. The actual history can still be wrong. Include the compensated drop/double example as a permanent negative control of the proof strategy: an image-only verdict must classify it as unproven, not exact-success.

## Recommended downstream decisions

1. Separate measured quantities: committed core frame/state; displayed frame; command dispatch/completion; screenshot freshness. Do not collapse these into one frame number. Fix a bounded sequence manifest containing expected relations and evidence identities. Preserve exact state snapshots at save points before overwriting host slot files.
2. Qualify a reused fixture over the entire possible startup/capture window, checked offsets, rewind range and run-ahead horizon. If any required step is observationally indistinguishable from zero/two steps or a wrong-load alternative, select generated marker content for those assertions. Do not merely check that two handpicked endpoint pictures differ.
3. Generate a small deterministic NROM guest with a visible marker wide enough not to wrap in the bounded window. Prefer predictable vblank updates and several marker bytes rather than a cycling palette alone. The marker is a guest/display counter, not automatically `frame_number`: startup, NMI latency and the rendered-frame pipeline require explicit calibration against `nesturbator_frame.frame_number`, saved state headers and marker decoding. Assert injectivity after startup and fail if the checked window extends outside qualification. Reuse owned fixture patterns where possible; no assembler/dependency required. Generated bytes remain build artifacts under existing asset policy; committed bytes require manifest admission.
4. Use native state validation to establish an anchor: bounded container extraction; exact format/length; expected content identity and current behavior revision recorded; load into a separately created same-content instance through the existing public API; compare the extracted state to independently generated uninterrupted reference state at its claimed frame when inputs permit. CRC-valid alone proves neither freshness nor the intended frame. CRC-32 is an identity/integrity convention, not cryptographic authentication; fixture SHA-256 separately identifies selected content.
5. Keep complete state/continuation/audio proof in existing portable core and simulated-host suites. A unique screenshot proves displayed sequence under the current configuration; it does not prove every machine field or absence of speculative audio leakage. A disk state anchor ties a save request to a committed machine boundary once freshness is established. Real-host claims must identify which of these they cover.
6. Share the verdict function between pure synthetic controls and real-host evidence. Feed it independently specified counterexamples; do not create negative expectations by running the same correct-step model and relabeling outputs. Real-lane mutation controls should withhold or double selected actions, use a valid wrong state with the same content, and verify they fail for the expected reason rather than process failure or missing artifact.

## Documented versus observed versus proposed

**Documented:** Official [NCI documentation](https://docs.libretro.com/development/retroarch/network-control-interface/) describes UDP commands, FRAMEADVANCE while paused, pause toggling, status queries, READ_CORE_RAM through achievements and READ_CORE_MEMORY through descriptors. The latter routes have capability requirements. The docs describe LOAD_STATE_SLOT's response but do not provide a transaction ID or establish that its reply proves the desired core state. Never infer a cross-command execution fence from a GET_CONFIG_PARAM reply.

**Documented conceptual model:** Official [run-ahead guide](https://docs.libretro.com/guides/runahead/) describes a single-instance committed frame saved before speculative visible work and restored afterward; two-instance mode separates primary audio and secondary video. Its detailed explanation dates to 2020. It supports distinguishing committed state from speculative display but does not prove exact 1.22.2 paused-command timing. Official [core development overview](https://docs.libretro.com/development/cores/developing-cores/) defines the frame/callback boundary; emulated software need not alter pixels at that boundary.

**Observed previously, not remeasured:** Phase13 reports GET_STATUS crashing 1.22.2, SAVE_STATE ignored after FRAMEADVANCE, run-ahead dropping running-session commands, and a RASTATE layout measured from files (`13-CONTEXT.md`, D-24/D-25; driver comments). Treat these as pinned-host constraints. Current public docs are not permission to replace them with assumptions.

**Proposed gates:** One bounded released-binary probe at execution start should determine whether (a) status queries are safe and attributable, (b) a save can be confirmed at checked boundaries, (c) disk save during run-ahead reflects the committed boundary, and (d) the chosen marker is displayed as calibrated after load and rewind. Retain binary/version/config/content identities, raw replies, states and images. Fail/restart on inconclusive action completion. Do not widen host platforms or add memory APIs to solve an oracle issue.

## Footguns and acceptance controls

- A RAM counter is attractive only when already exposed through a supported read-only route. Here it would require new adapter support/capability probing; it reads guest logic rather than a complete state and can reflect different timelines during run-ahead. Prefer visible markers plus save transport within Phase16. Never use memory writes as an observation mechanism.
- Full-pixel equality is a deterministic host-conversion check, not independent hardware conformance. A host and reference library can share a rendering bug. Independent verdict controls and a directly decoded marker prevent transport/oracle agreement from becoming self-confirmation.
- Pause: equal pictures at two times cannot establish pause for static content or duplicate frames. Safe attributable PAUSED status is strongest where supported; otherwise a qualified advancing marker plus fresh separated observations establishes bounded no-progress evidence, not universal scheduler state. Retain an unpaused/static-picture negative control.
- Rewind: current 40 paced REWIND requests with at least20 frames backward establishes bounded reverse progress, not exactly40 actions. Preserve that truthful claim unless the pinned host yields independent per-action evidence. Verify post-rewind advance and load from the saved rewound anchor, not merely a lower image candidate.
- Run-ahead: assert displayed m+1+k and, if validated transport supports it, committed m+1 after one real tick; never require a disk state at displayed m+1+k. Test wrong lead, disabled toggle and wrong-load origin with distinct markers. If save timing prevents committed observation, explicitly retain that part as simulated-host evidence only.
- Freshness: one outstanding artifact request, isolated generation paths, preserve original filenames and command ledger, require complete parse/read and stable publication. New filename or changed checksum alone is insufficient attribution. Identical state saves can validly have identical bytes; byte change must not be the only completion test. Late screenshot from step n must fail/quarantine rather than become n+1. Restart after an unconfirmed non-idempotent action; never blind retry FRAMEADVANCE or PAUSE_TOGGLE.
- Parsing: cap file sizes/chunks/frame windows and candidate counts before allocation; reject truncated/overflow lengths, duplicate MEM chunks, unexpected compressed formats, ambiguous trailing data and out-of-window frame values. Support only the pinned observed envelope unless a fresh binary demonstrates a change. Fail malformed inputs distinctly from a wrong progression verdict.

Required pure verdict controls: valid intended history passes; isolated drop and double fail when distinguished; compensated drop/double with identical pixels and matching endpoint anchors is unproven; incompatible branch origins fail; valid same-ROM wrong-frame load fails; corrupt/wrong-ROM state fails before anchoring; stale/duplicate/out-of-order screenshots fail attribution; run-ahead display and committed counts cannot be exchanged; failed parse cannot satisfy expected semantic failure. Run these through the production verdict entry point in normal ci on supported platforms. Keep hosted controls finite and measure their added wall time before setting deadlines under ENGINEERING's existing timeout policy.

### Compound paused-load confirmation

The command advisor correctly identifies a special compound boundary. The inherited pinned-binary observation is that a paused LOAD_STATE_SLOT 0 does not redraw, so require one planned load followed by **exactly one planned FRAMEADVANCE**, then confirm the unique displayed marker at the preserved save origin plus one (or plus one and the configured run-ahead lead). Send each action once; the advance is the discriminating load probe, never a retry. Do not require the screenshot between load and advance to equal the saved frame, do not treat echoed slot receipt as restored-state proof, and do not claim load completion was independently observed before the advance.

A wrong-load control uses a valid same-ROM state at a different calibrated marker origin; after the one advance it must display the wrong marker and fail the production verdict. Choose that alternate origin outside startup and within the qualification window. A dropped load must continue from a current position deliberately different from the saved origin; otherwise a no-op can accidentally satisfy the expected result. A doubled probe advance must produce saved-origin+2 and fail, including run-ahead mode where the displayed result is saved-origin+2+lead. These conditions must be selected explicitly rather than inferred from the absence of a host error log.

Preserve both original slot states before any overwrite, validate their whole-machine payload through the existing state API, and bind each to content identity, the calibrated displayed marker and its recorded absolute frame. All branches use that specific anchor; do not allow a different candidate origin per branch. For the original save with run-ahead off, require the anchor's core frame and marker's calibrated display frame to agree at the known boundary. For the rewound save, require the same relation and a bounded backward difference from the recorded pre-rewind marker. Loading that preserved anchor plus one advance then establishes the intended displayed continuation and selected origin within the bounded fixture sequence. Whole-state equality/continuation remains independently covered by the portable tests; an apparent same-origin machine corruption that preserves a marker is not ruled out by pictures alone.
