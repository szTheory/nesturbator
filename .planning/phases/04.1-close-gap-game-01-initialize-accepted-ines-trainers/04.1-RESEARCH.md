# Phase 04.1: Close gap: GAME-01 — initialize accepted iNES trainers - Research

**Researched:** 2026-10-09  
**Domain:** C NES cartridge loading and CPU bus mapping  
**Confidence:** HIGH for the documented trainer layout and observed code gap; MEDIUM for the minimal RAM ownership recommendation because the current supported mapper-0 RAM profile intentionally excludes declared PRG RAM.

## Summary

The audit's defect is reproducible by source inspection: the accepted image parser accounts for a 512-byte trainer, and `nesturbator_load_cartridge` starts PRG after that payload, but it discards the trainer from reachable cartridge state. The CPU bus decodes internal RAM, PPU registers, I/O and PRG ROM at `$8000+`; no path serves `$6000-$7FFF`. Thus accepting the header and validating payload geometry does not produce the documented trainer memory contents. [VERIFIED: `.planning/v1-MILESTONE-AUDIT.md`, “GAME-01 — Trainer data is accepted but not applied”] [VERIFIED: `src/cartridge.c:69-70,151-168`] [VERIFIED: `src/bus.c:50-58`]

NESdev's iNES format documentation specifies a fixed 512-byte trainer stored before PRG and loaded at CPU address `$7000-$71FF`; its NES 2.0 format page likewise describes 512-byte trainer data loaded at `$7000`. These are the hardware-visible initial bytes to preserve. The project preparation index already pins the format sources as HWP.14 (iNES revision 23194; NES 2.0 revision 24342). [CITED: https://www.nesdev.org/wiki/INES] [CITED: https://www.nesdev.org/wiki/NES_2.0] [VERIFIED: `.planning/preparation/NES-HARDWARE-PPU-CARTRIDGE.md`, sections 1 and 6; HWP.14]

**Primary recommendation:** Keep supported trainer-bearing mapper-0 files accepted and make `$6000-$7FFF` writable, instance-owned PRG RAM available for them; copy the 512 payload bytes to RAM offset `$1000` (CPU `$7000`) before the CPU begins from its reset vector. Exercise the behavior through the existing core bus in a synthetic in-memory ROM test; do not add a dependency or checked-in ROM blob. Update the API comment and README in the same behavior change. This is the smallest implementation that closes the accepted-input promise and exposes the initialized data through the same address path games use. The exact initialization timing is not required to prove the audited contract; do not execute trainer code or add CPU-cycle startup work unless the planner identifies an explicit cited requirement.

## Architecture Patterns

### Data flow

```text
iNES/NES 2.0 input
  -> validate header and exact file geometry
  -> retain trainer span (16-byte header + 512-byte payload)
  -> allocate/initialize per-instance mapper-0 PRG RAM
  -> copy payload to RAM offset 0x1000 (CPU $7000)
  -> reset CPU from PRG vector
  -> CPU bus reads/writes $6000-$7FFF against that RAM
```

### Recommended implementation boundaries

1. Keep image validation before allocation. The existing loader allocates only after `validate_image` succeeds; preserve the rejected-file/no-allocation property.
2. Preserve independent pointers/lengths for PRG, CHR, trainer, and RAM. Do not reinterpret the trainer as PRG data: existing `offset = 16u + layout.trainer_size` deliberately keeps PRG aligned after it.
3. Store RAM in the cartridge/instance ownership lifetime, zero it on a new load, and free it on unload/reload through the existing allocator. If adding a RAM allocation requires a second allocator call, test allocation-failure cleanup and transactional reload semantics; preferably keep ownership simple and consistent with the current single cartridge allocation.
4. Decode the `$6000-$7FFF` range in both bus read and write paths. Use offset `addr - 0x6000`; trainer data belongs at RAM offset `0x1000`, covering offsets `0x1000..0x11FF`. Neighbor bytes must remain writable RAM and not alias PRG ROM.
5. Keep trainer RAM state per instance. Do not use static storage or couple it to global runner/libretro state.

## Common Pitfalls

### Copying trainer bytes into PRG ROM or shifting the PRG pointer incorrectly

**What goes wrong:** `$8000+` reads become corrupted, or the 512-byte trainer is mistaken for the beginning of PRG.  
**Why:** Trainer data sits between the header and PRG in the file, but belongs at `$7000` in CPU-visible writable RAM.  
**How to avoid:** Keep the existing PRG offset calculation and maintain a separate trainer/RAM destination. Assert the reset vector still comes from the last four PRG bytes.

### Mapping only the trainer's exact 512 bytes

**What goes wrong:** The trainer reads correctly, but accesses elsewhere in the cartridge RAM window remain open bus or alias incorrectly.  
**How to avoid:** Implement the intended 8 KiB `$6000-$7FFF` RAM window for trainer-bearing accepted images and place the payload at its `$1000` offset. Verify lower/upper boundaries.

### Allocating RAM before validation, or leaking it during failed reload

**What goes wrong:** Malformed files violate GAME-01's counting-allocator invariant or the prior loaded cartridge is lost on allocation failure.  
**How to avoid:** Validate first; prepare all needed storage before replacing existing cartridge state; preserve cleanup symmetry. Add a failure-path assertion if storage introduces a new allocation.

### Forgetting that loader acceptance and README/API promises are part of the fix

**What goes wrong:** Implementation works but continues to document a weaker or ambiguous contract.  
**How to avoid:** In the same change, specify trainer initialization at `$7000-$71FF` and the supported RAM scope in `include/nesturbator.h` and README. Keep unsupported mapper/RAM configurations rejected as before.

### Adding a binary fixture unnecessarily

**What goes wrong:** Adds licence and hygiene work with no additional coverage value.  
**How to avoid:** Construct the small image in the existing test helper; add no ROM file or external fetch.

1. **(RESOLVED) Should 8 KiB PRG RAM exist for all supported mapper-0 images or only trainer-bearing images?** Only accepted trainer-bearing mapper-0 images receive instance-owned 8 KiB PRG RAM, per the user-approved phase scope.
