## Decisions taken under Claude's discretion, and research open questions resolved

- **Open question 1 (24 KiB total RAM, research C5): rejected.** V + N must be 0, 8, 16 or 32 KiB. No board has 24 KiB and the bank formula has no case for it. This stays within D-08 (each of V and N is still 0, 8, 16 or 32 KiB) and adds the seed `mmc1-ram-24k` and a cartridge row.
- **Open question 3 (trainer + mapper 1 + no declared RAM): the trainer's 8 KiB maps at `$6000` as work RAM, and the span is NULL/0.** The allocation exists (D-06 keeps the trainer path), so the page maps; `core.save` has a one-line case. With declared NVRAM and a trainer, the trainer lands at `prg_ram + 0x1000` and a later `.sav` overwrites it inside the span (D-06).
- **Span write recognition (D-12 discretion): a range check in `nesturbator__bus_write`**, guarded by `save_size != 0`, right after the page store. Every `cpu_w` page lies inside the single `cart.bytes` allocation, so the pointer compare stays within one object (research Pattern 5).
- **Zero encodings (D-16 discretion, research C2):** `control_x` stores `control ^ 0x0C`, so zero means `$0C`; `last_write` stores `stamp + 1`, so zero means "never written". A comment cites NESdev Wiki "MMC1".
- **`nesturbator__map_prg_ram` is generalised, not duplicated:** the new `nesturbator__map_prg_ram_8k(nes, ram_8k)` takes a bank pointer or NULL, and the existing helper becomes a one-line call with bank 0, so the trainer boards keep their call.
- **Reversibility, no checkpoint:** D-11 is rated one-way and D-06 costly in CONTEXT.md. The owner chose these exact options in discuss-phase, so Task 1 keeps the one-way rating for the record and no `checkpoint:decision` re-asks it (planner-reversibility: do not gate a decision already made). D-06's costly layout is frozen by the `core.save` invariant test and stated in the header and README.
- **Header guards land in Task 1 with the declarations**, so `vectors.api_policy` is never red between commits; README text lands in Task 3, inside the same pull request (CLAUDE.md rule 6).

<assumption_delta_decision>
The detector fired on the words "another" (another write) and "second" (a second run) in the roadmap text. Neither names a second identity: they describe the MMC1 write rule and the runner's second run. The real generalisation in this phase is PRG-RAM: it was one flat 8 KiB block that only the trainer path created, and it becomes a per-cartridge allocation of 0-32 KiB laid out `[V work][N NVRAM]`, with the save span a view into it.

- **Primary noun:** the cartridge's PRG-RAM allocation (`cart.prg_ram`, `cart.prg_ram_size`). The span (`cart.save`, `cart.save_size`) is a view into it, never a second allocation.
- **Decision:** promote. The trainer's 8 KiB becomes one case of the general allocation (`ram_total = max(V + N, trainer ? 8 KiB : 0)`), and `nesturbator__map_prg_ram` becomes a bank-taking helper that every board uses. Nothing is added alongside the old flat block.
- **Invariant test (accepted):** `core.save` asserts, for every D-07 header case, that `save == prg_ram + V` and `save_size == N`. A later phase that reintroduces a second RAM block would fail it.
</assumption_delta_decision>
