## Timeline identity: why and how (implements the D-16 amendment of 2026-10-25)

D-16's frame_number tag alone lets a state from a diverged timeline (rewind or a second save slot, different input, same frame number) show the other timeline's picture on a JAM. The owner amended D-16 on 2026-10-25 during plan check (19-CONTEXT.md, D-16 "Amendment" sub-bullet): the tag also carries a timeline identity (state CRC), a load into a different timeline invalidates it, and a misprediction ending in a JAM on the first real frame after a load shows black as an accepted residual. A generation bumped on every successful load would break run-ahead itself (every tick loads), so the generation moves only when the loaded state is not one the cached frame belongs to. Identity is the state CRC that `nesturbator_save_state` writes at header offset 28: the adapter saves the instance into its scratch buffer after each converted frame (records `cached_state_crc`) and after each STOP_JAM run while the cache is current (records `jam_state_crc`). Recording at conversion rather than only in `retro_serialize` keeps RetroArch's second-instance run-ahead correct, where the instance that shows the picture never serializes. Cost: one `nesturbator_save_state` per converted frame, inside the adapter only; the core is unchanged. This save is kept rather than gated: conversion is the only point where the showing instance sees the state its picture belongs to (it never serializes under second-instance run-ahead, and the adapter cannot tell whether a host runs ahead), so no smaller trigger reaches the same property. Task 2 measures its time and bytes against one frame run and records them in the SUMMARY; no CI performance gate is added. Every other D-16 rule holds unchanged: the tag is the frame_number, a successful unserialize does not invalidate the cache by itself, a mismatch shows black, reset/load_game/unload invalidate, a refused load preserves, nothing enters the native state.
