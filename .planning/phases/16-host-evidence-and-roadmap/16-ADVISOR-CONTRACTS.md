## Exact fixture identity — EVID-03

| Option | Pros | Cons | Complexity | Recommendation |
|--------|------|------|------------|----------------|
| Exact basename plus manifest-backed identity check in the registered-test wrapper | Preserves host CLI, existing CMake SHA256 and manifest machinery, parent path cannot choose role | Guard is at controlled test boundary, standalone host calls do not authenticate bytes, copy checks must be ordered before execution | Host dispatch, CTest registration and one small CMake helper -- Risk: wrapper bypass or stale copied bytes | Rec if registered CTest invocations are the declared evidence boundary; preferred minimal approach |
| Exact basename plus in-process size and byte equality against explicit canonical references | Validates the already-read bytes, wrong bytes under a valid name fail inside host, no crypto implementation | Adds canonical-reference parameters and extra reads, must avoid silently reading the supplied candidate as its own reference | Host fixture helper and test-only CLI/CMake arguments -- Risk: incorrect reference wiring | Rec if direct host invocations must enforce the full identity contract |
| Explicit per-ROM role argument plus independent byte validation | Role survives harmless fixture renaming, errors are attributable to named roles | Additional argument pairing/validation, role alone is only a caller assertion, unnecessary for two fixed special fixtures | Host test CLI and every affected CTest invocation -- Risk: wrong role paired to valid content | Rec if fixtures acquire multiple legitimate aliases or roles |

**Rationale:** Fix both full-path substring decisions with one small owned final-component helper and exact case-sensitive comparisons. The existing fixtures have stable names and manifest hashes, so explicit roles are currently extra interface surface. Prefer existing CMake SHA256 for the registered-test boundary; choose size plus full byte equality in-process if the evidence contract includes direct host invocation. Basename matching alone solves path redirection, but does not establish that a trusted name contains the expected bytes. FNV is suitable for ordinary test discrimination, not adversarial authentication.

Observed evidence:

- `tests/libretro/libretro_host.c:2029` enables MMC1 battery checks whenever the full path contains `M1_P128K_C128K_S8K`; `:2395` enables the full run-ahead/control matrix whenever the full path contains `nesteroids`. These are the two actual selectors. `ser_prepare` at `:1490` reads bytes and prepares state but performs no fixture identity check.
- `tests/CMakeLists.txt:1319` registers serialization with five ROMs and `:1336` run-ahead with seven ROMs plus generated stress images. Preserve current board coverage, control counts and no-work guards rather than using a name fix to reduce work.
- `tests/roms/manifest.txt:20` pins nesteroids SHA256 `a30dcfb12c1447dc121619c93b4083d2b83c7405a883ed490c3a59e52ce74f36`; `:63` pins MMC1 battery SHA256 `2263d212fe9c8e857f89c846962e7e78f3ba885e1413644b94e50cfff65ecd08`.
- `tests/CMakeLists.txt:1597` registers `manifest.sha256` and its wrong-hash selftest. Merely running this independent source-tree test does not authenticate a copied candidate; the copied input itself must be checked before the host receives it.

Acceptance and controls:

1. For each special fixture, ordinary path and copied path under parents containing both trigger strings select the same intended role, with the same required control/battery counts. A generic ROM under either trigger parent never receives a special role. Preserve original manifest-listed ROM bytes; copies/generated mutations stay in build scratch directories.
2. Test exact names, similar names such as `nesteroids-extra.nes`, `copy-nesteroids.nes`, `M1_P128K_C128K_S8K.nes.bak`, empty/final-directory components, paths with spaces, and platform separator behavior. Define this as basename extraction for supported path syntax, not realpath/security canonicalization. Windows separators need coverage; on POSIX a literal backslash may be a filename character, so avoid asserting unsupported normalization semantics.
3. Wrong image under a recognized basename, changed byte, truncation and unexpected extra bytes fail identity validation before special controls execute. Unknown ordinary fixtures may continue ordinary board coverage; a declared special identity mismatch must fail rather than silently downgrade and still produce a green suite.
4. If explicit roles are chosen, unknown role, duplicate special role, missing role and wrong-role/content pairing fail with a specific diagnostic. Role cannot override validation.
5. Restoring either old `strstr` selector must make the adversarial parent tests fail. The controller test should assert selector outcomes/counts explicitly, not merely accept a broad nonzero exit from some unrelated late assertion.

Security limit: this prevents evidence misclassification in controlled tests. It does not claim hostile concurrent-filesystem protection or a ROM authenticity service. A SHA check followed by a path reopen is adequate only under the stated controlled fixture boundary; validating the already-loaded bytes is stronger if that boundary changes. No game database, new parser or core loader feature is needed.

## Truthful narrow MMC3 metadata — EVID-04

| Option | Pros | Cons | Complexity | Recommendation |
|--------|------|------|------------|----------------|
| Concise qualified description plus bounded MMC3 facts check | Small delta, preserves human prose, reuses existing info parser and loader tests | Semantic fields need a stable declaration in docs to avoid fragile sentence matching | Info, README/header, existing claim checker/selftest and loader cases -- Risk: overly broad tokens or circular doc-only agreement | Rec if the support contract remains a short fixed set; preferred approach |
| Small MMC3-specific support table/declaration checked against generated loader cases | Precise accepted/excluded profiles, formatting-independent facts, easier maintenance of boundaries | Adds a little local duplication, must keep it specific rather than growing a universal schema | README/header declaration, CMake check and loader test linkage -- Risk: turning a narrow test into a profile registry | Rec if current prose cannot expose testable semantic boundaries simply |

**Rationale:** Released metadata should say NTSC and MMC3 while naming the implemented profiles narrowly. Keep the existing loader as the authority and use owned generated cases plus existing tests as behavioral proof. An automated consistency check should compare support facts, allow normal prose edits, and reject drift; no dependency or generated global mapper registry is justified.

Observed evidence:

- `libretro/nesturbator_libretro.info:24` currently lists NROM, MMC1, UxROM, CNROM and AxROM; MMC3 is missing. This is an under-description, not a reason to advertise every mapper-4 variant.
- `README.md:1149` and `include/nesturbator.h:301` agree on mapper 4: submapper 0 (Sharp, also iNES 1) and 4 (NEC), power-of-two PRG 16–512 KiB, CHR ROM 8–256 KiB or 8 KiB CHR RAM, PRG RAM none/8 KiB work/8 KiB battery with matching battery flag. MMC6, remaining submappers, four-screen, CHR NVRAM/other RAM sizes and neighboring mapper IDs are excluded.
- `src/cartridge.c:128` implements mapper-4 admission. `tests/core/test_cartridge.c:591` has valid and invalid MMC3 cases, including valid NEC at `:596`, rejected submappers at `:609` and rejected four-screen at `:615`. These supply actual behavior rather than a documentation-only agreement loop.
- `tests/cmake/info_claims.cmake:21` classifies `description` as metadata, while `:17` associates serialization claims with tests. Its parser and selftest are reusable, but its current guard does not prove board-description truthfulness. `tests/CMakeLists.txt:1819` wires this guard and CTests into existing CI.
- `README.md:549` separately records 10/12 MMC3 oracle passes and two revision-specific unsupported results. Admitting NEC submapper 4 does not imply every NEC timing test passes; retain that distinction.

Suggested description meaning, with final prose discretionary: an NTSC NES core supporting NROM, MMC1, UxROM, CNROM, MMC3 (mapper 4 submappers 0/4; no MMC6 or four-screen), and AxROM, with battery saves. This is a paraphrased proposal, not an accuracy guarantee. Detailed size/RAM limits remain in README and public header, referenced by the consistency evidence.

Acceptance and controls:

1. Parse the actual checked-in `.info` with the existing parser and validate its single description field. Require MMC3 in a positive support context and the accepted submapper scope; do not accept a description that says only MMC3 is unsupported because it contains the token. Preserve existing feature claims unless changed by separate evidence.
2. Compare bounded semantic facts with a small explicit support declaration in the existing README/header comments if needed: mapper=4, supported submappers={0,4}, MMC6=no, four-screen=no. Verify described accepted/rejected profiles by existing loader cases or a tiny owned submapper sweep. Keep original detailed size/RAM tests credited. Surrounding punctuation, wording and formatting should not be a contract.
3. Mutate metadata/docs independently: remove MMC3, add submapper 1 or all-submappers, drop exclusions, contradict header/README, duplicate description key. Each must fail the intended check with an attributable diagnostic. A harmless prose edit passes. No claim that arbitrary natural-language exaggeration can be detected mechanically.
4. Ensure generated package/staged adapter metadata is the corrected source `.info`; do not claim a release has been published until the normal release pipeline provides actual publication evidence. Public metadata beyond this repository/distribution remains outside scope.

Official source meaning: the [libretro example info file](https://github.com/libretro/libretro-super/blob/master/dist/info/00_example_libretro.info) distinguishes supported extensions, hardware identity, feature flags and descriptions. The [official core-development documentation](https://docs.libretro.com/development/cores/developing-cores/) explains the matching `.info` filename and frontend-visible information, and distinguishes memory-loaded content from file paths. Neither source promises that `supported_extensions=nes` means every NES board works. Accessed 2026-10-13. The initially attempted pinned example URL was unavailable; the current example was fetched instead, without opening emulator implementation source.

## Adversarial cross-review

Reviewed sibling progression and commands reports on 2026-10-13. No new runtime evidence, repository edits or dependencies. Their conclusions agree with this report: filenames are not byte identity, screenshots are not necessarily exact frame observations, and current documentation is not proof of pinned-host command behavior. The following resolutions narrow the combined recommendation.

**Choose the controlled registered-CTest boundary for EVID-03.** Use exact final-component comparisons in both existing selectors, with a small CMake wrapper that checks each supplied/copied special input against its existing manifest SHA256 before invoking the host. Source-tree `manifest.sha256` alone cannot authenticate a relocated input. Name all boundary claims explicitly: registered tests enforce this identity policy; arbitrary direct `libretro.host` calls are not newly authenticated. In-process canonical references and explicit role arguments remain alternatives, not additions to the preferred patch. Treat basename similarity as no special role, but recognized special basename with wrong bytes as a fail. Case/path behavior must be platform-defined; do not introduce realpath canonicalization or a generic filename security service.

**Give generated marker content its own identity and calibrated role.** The progression report's fallback marker fixture must not be renamed to nesteroids or selected by a containing parent path. Its generator owns deterministic bytes; the wrapper can compare the candidate against that generated expected artifact using existing CMake hash facilities, recording the generation parameters and hash. The oracle must explicitly bind the new content identity to its startup/marker-to-frame calibration and qualified window. Existing nesteroids run-ahead controls, seven-board coverage and serializer battery coverage remain credited and preserved. Selecting a marker for real-host exactness does not automatically replace the existing special fixture or justify changing its guards. A same-ROM wrong-frame state must pass content identity and fail progression; wrong-ROM bytes under the trusted name must fail identity earlier. Diagnostics and controls must distinguish those stages.

**Shrink metadata enforcement to one localized support clause and existing behavior proof.** The minimum viable guard need not infer arbitrary prose: parse `.info` with the existing parser, require one positive, deliberately stable MMC3 support clause that names mapper 4/submappers 0 and 4 and excludes MMC6/four-screen, and allow surrounding descriptive prose to vary. Put the same compact semantic facts near the existing README/header support comments only if the existing facts cannot be checked simply. This is an intentional local declaration, not a global mapper registry, general admission schema, complete text snapshot or natural-language parser. The consistency check should couple those narrow declarations with the registered existing `core.cartridge` behavior tests, whose mapper-4 rows already accept 0/4 and reject excluded profiles; do not duplicate every RAM/size test or generate all board metadata. An example shape for the localized clause is a positive Supported MMC3 heading/list item with accepted={0,4}, MMC6=no, four-screen=no; exact prose/notation is implementation discretion. Mutants removing MMC3, changing accepted profiles or contradicting exclusions fail, while unrelated wording changes pass. Fixed literal facts inside the narrow declaration are acceptable; matching the entire description or entire public-header prose is not.

**Resolve command/oracle causality without widening identity scope.** The commands report correctly allows a planned LOAD_STATE_SLOT plus single FRAMEADVANCE compound when paused loading does not redraw. Identity validation occurs before the attempt, then freshness and the calibrated marker/state anchor determine whether the compound succeeded. A read reply is never a load fence. Failure because an artifact is absent/malformed must not count as a successfully discriminated wrong-load control. Generated fixture identity and frame injectivity do not establish command exactly-once delivery for arbitrary delayed duplicates; retain the bounded local-session claim and fail ambiguous actions once, with no silent retry-to-green.

**Keep roadmap and publication claims independent and honest.** DIR verification remains the one-time inspection of installed links, stable approved RM IDs, both milestone instructions and actual v4 opening reconciliation. Do not run another new/complete-milestone step, patch global workflows, force a recurring validator or simulate closeout. At Phase 16 completion, acceptance evidence can establish delivery of the instruction contract; it does not establish future compliance. Metadata may be validated in the staged/package artifact before publication, but released/shipped wording waits for actual release evidence. Neither a merged PR nor passing packaging alone is a published release. RM-001/RM-003 and future proposals remain pending/proposed; SEED-006 remains recurring.

**Diminishing returns:** The combined reports now cover the concrete counterexamples and decision boundaries. Further framework, governance or emulator research would add little. The next useful evidence is bounded implementation-time execution of the shared oracle controls, pinned-host capability/calibration probe, copied-fixture identity controls, localized metadata mutants and measured CI cost. Remaining uncertainty should be resolved by those tests, not extra research fanout or speculative machinery.
