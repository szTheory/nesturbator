## Decisions taken under Claude's discretion

- **`$A001` encoding (D-08):** the field `a001_x` stores the written byte XOR `0x80`, so zero means bit 7 set (enabled) and bit 6 clear (writable). Comment cites NESdev "MMC3" ($A001 power-on unspecified) and D-08.
- **Fall-index boundary (D-05):** clock iff `nes->cpu_cycle - reg.mmc3.low_cycle >= 3`. Research Summary item 2 shows that inside a hook `cpu_cycle` equals the number of M2 falls strictly before the dot, so the difference is the number of falls between the two edges. D-09's original "72-tick gap spans only two falls" case does not hold under the D-05 derivation; D-09 now carries a dated amendment (2026-10-10, 09-CONTEXT.md) that restates the hook-level boundary case in CPU-cycle units (2 filtered, 3 and 4 clock), which is what PITFALLS pitfall 7 asks for and RESEARCH open question 2 (RESOLVED) records. D-05 (locked) is implemented as written.
- **`mapper.h` hook rule:** the hook-rules comment is amended to say `ppu_a12` may read `nes->cpu_cycle`, the count of completed CPU cycles, as its M2 fall clock; no hook argument is added (no internal ABI churn).
- **Loader docs:** README and public-header text for mapper 4 land in this plan (Task 2), in the same change as the loader row (CLAUDE.md rule 6). The runner's message and `--rom` text belong to Plan 07, which changes the runner; the Holy Mapperel paragraphs belong to Plans 08 and 09.
- **Fuzz seeds:** the `valid-mmc3` seed and its manifest line belong to Plan 02, which starts the D-16 seeds; this plan proves the loader through the public API and the CPU.
- **Behaviour revision stays 5:** no existing board's output moves; Phase 8 added mapper 1 under the same revision.
