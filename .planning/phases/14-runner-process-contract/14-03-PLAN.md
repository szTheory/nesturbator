  <action>
Per D-24 add `### Stopping the runner` to `## The runner`, directly before `### Exit status`, containing these sentences verbatim (they are what the guard matches): `On SIGTERM or SIGINT the runner finishes the current frame, writes the battery save and exits 0, or 1 if the save could not be written.`; `A second signal at any time, including during the flush, ends the runner at once.`; `On Windows the runner handles Ctrl+C, Ctrl+Break and console close the same way.`; `A forced termination (TerminateProcess, taskkill /F, power loss) cannot be handled; the last committed .sav survives it.`; `A launcher that sends the event to group 0 first registers its own handler that returns TRUE for CTRL_BREAK_EVENT, after attaching and before sending, or the event ends the launcher too.`

Around them, in the same section: the stop line on stderr and that nothing is added to stdout; that the stop is seen between frames, also before the first frame when it arrives during loading, and that a load error keeps its own status; that the save goes through the same temp-and-rename write, so it is never torn; that SIGTERM is not a Windows mechanism. The Windows launcher recipe (per D-24 and research implications 1-2, D-16 order) states its console precondition explicitly, in two cases. Case one, the launcher shares the runner's console: it starts the runner with `CREATE_NEW_PROCESS_GROUP` (and without `CREATE_NEW_CONSOLE`, `DETACHED_PROCESS` or `CREATE_NO_WINDOW`) and stops it with `GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, pid)`, the runner's process id being its group id, so only the runner's group gets the event. Case two, the launcher has no console or a different one: it starts the runner with `CREATE_NEW_CONSOLE`, detaches from its own console (`FreeConsole`), attaches to the runner's (`AttachConsole` with the runner's process id), then registers its own TRUE CTRL_BREAK handler with `SetConsoleCtrlHandler` (after attaching, because attaching resets the handler list), and only then sends `GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, 0)`; group 0 reaches every process on that console, the launcher included, which is why the launcher's own handler is required (the guarded sentence above). Never send CTRL_C_EVENT to a process group. Also: no event reaches a runner started with `DETACHED_PROCESS` or `CREATE_NO_WINDOW`, and logoff and shutdown are not handled; the launcher must read or discard the runner's stdout, because the runner flushes stdout before the save (research Pitfall 12, Open Question 4); `--raise-after` is a test aid that signals the runner's own process, with SIG `int` or `term` on POSIX (default `term`) and `int` or `break` on Windows (default `break`, research Pitfall 7). Add `--raise-after` to the README's option list with the same defaults (D-11). In `### Exit status` extend the When cell of row 1 with `a stop whose save could not be written`.
