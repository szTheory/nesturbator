## Summary

Phase 03 is a vertical integration phase across the existing C library, runner, libretro adapter, and CTest/Actions harness. The essential architectural decision already settled is that the core owns deterministic emulated state and native pixels, while the runner and libretro adapter are host layers. Preserve that split: implement NROM mapping and PPU state inside the instance; expose content lifecycle, frame execution, and controller state through the public API; keep file parsing and movie serialization in the runner. The existing libretro seam should remain a thin bridge to the same API, using host joypad callbacks and the existing palette conversion path.

The implementation risks concentrate at boundaries: hostile file sizes must be rejected without cartridge allocation; instruction execution can cross a requested frame tick; PPU vblank/NMI and rendering behavior are dot-sensitive; controller reads are serial and strobe-sensitive; and pixel hashes must exclude display calibration. Treat a game's boot and first stable visible frame as a broad end-to-end oracle, not as a substitute for targeted PPU, CPU, loader, controller, and AccuracyCoin tests. Make all recurring machine-verifiable checks required CI gates, with only the RetroArch executable launch isolated to the pinned macOS end-to-end job.

**Primary recommendation:** plan an end-to-end tracer slice that boots one pinned CHR-ROM NROM game through runner and RetroArch, then expand to CHR-RAM and two-player coverage while preserving the same shared core API and automated gates.

## Architecture Patterns

### Recommended Project Structure

Follow the current `src/`, `runner/`, `libretro/`, and `tests/` modules. Add small internal modules for cartridge parsing/mapping, PPU stepping/rendering, controller state, and movie/fixture tests only where implementation scope requires them; preserve private implementation headers and existing CTest registration conventions. In-repo path anchors read from source this session: CMake builds `src/frame.c` (`CMakeLists.txt:54`) and the runner code is `runner/main.c`; do not infer a prescribed future path from these existing names.

### Pattern 1: Validated cartridge ownership boundary

**What:** Parse header fields into checked integers, validate mapper/submapper, format, supported board geometry, declared payload lengths, and permitted trailing sections before creating cartridge-owned state. Only after validation succeeds allocate/copy the minimal cartridge data. On all rejection paths, counting allocator remains unchanged. `retro_load_game` should pass the in-memory content buffer through the public loader and unload should destroy exactly that instance's cartridge data.

**Why:** The iNES/NES 2.0 header is untrusted input. NES 2.0 has exponent/multiplier sizes and RAM declarations; unchecked arithmetic can overflow and drive giant allocation attempts. `[CITED: https://www.nesdev.org/wiki/INES]` `[CITED: https://www.nesdev.org/wiki/NES_2.0]`

**Pitfall to avoid:** Treating every mapper-0 file as exactly 16-byte header + PRG + CHR ignores trainer offset and format-specific optional data; accepting opaque trailing bytes without a deliberate support/reject policy can silently misread content. Keep accepted layouts narrow and document policy.

### Pattern 2: Per-dot integrated PPU with a frame request boundary

**What:** Advance CPU and PPU from the established integer tick model; PPU performs real background/sprite fetch and register side effects as part of the shared bus, and frame output is produced at a documented boundary. Retain residual timing when an instruction steps past the target frame tick; the next call must not execute that overshoot twice or skip input/frame state.

**Timing hazards:** In current source, “one tick is half a master-clock period; NTSC has 24 ticks per CPU cycle and 8 per PPU dot” and the current `NESTURBATOR_TICKS_PER_FRAME` is `714732u` (`src/internal.h:8-12`). `[VERIFIED: src/internal.h:8-12]` Quote: “one tick is half a master-clock period; NTSC has 24 ticks per CPU cycle and 8 per PPU dot” / “#define NESTURBATOR_TICKS_PER_FRAME 714732u”. These are the current baseline, not a claim that every odd frame has the same exact dot pattern. The preparation reference describes vblank set/clear, `$2002` suppression windows, odd-frame skip, open bus, and dot-visible register behavior; the plan must use those tests to pin ordering rather than invent line-batched shortcuts. `[CITED: .planning/preparation/NES-HARDWARE-PPU-CARTRIDGE.md §2-4; https://www.nesdev.org/wiki/PPU]`

**Pixel/hash contract:** `src/internal.h` defines the existing dimensions as `NESTURBATOR_WIDTH 256u` and `NESTURBATOR_HEIGHT 240u` (`src/internal.h:19-21`). `[VERIFIED: src/internal.h:19-21]` Quote: “#define NESTURBATOR_WIDTH 256u” / “#define NESTURBATOR_HEIGHT 240u”. Hash row-major native pixels in a platform-independent byte order; perform NTSC-to-sRGB conversion only in host output. Existing `runner/main.c` documents SHA-256 over native pixels as little-endian uint16 values (`runner/main.c:10-11`). `[VERIFIED: runner/main.c:10-11]` Quote: “The hash is SHA-256 over the 256x240 native pixels as little-endian `uint16_t`, row-major, top row first; never over the image”.

### Pattern 3: Per-frame controller snapshots, serial reads, shared replay path

**What:** Represent controller state as a deterministic frame input; latch button state when emulated strobe behavior requires it, then shift the NES-defined order as CPU reads occur. Port 1 and port 2 use separate state. Runner script and movie decoder supply the same masks directly; libretro polls once per frame then maps standard joypad IDs into those masks. Test strobe-high repeated reads, high-to-low latch, bit order, post-eight reads, and independent ports.

**External contract:** Libretro docs say a core should poll input at least once and call the video callback exactly once for each `retro_run`; its RetroPad abstraction lets frontends map hardware and software devices. `[CITED: https://docs.libretro.com/development/cores/developing-cores/]` `[CITED: https://docs.libretro.com/development/input-api/]` Therefore test button mapping through the host seam with callback fakes; physical DualSense pairing is optional manual play only.

### Pattern 4: Deterministic movie with explicit framing

**Recommendation:** Choose a minimal owned binary or text format with magic, version, frame count, and fixed-width per-frame port masks. Reject unknown versions, truncation, invalid header/length, overlong frame counts, and trailing junk according to a documented policy. Decode and validate before execution so malformed input cannot partially mutate emulated state. Reset the emulated instance before every replay, and compare outputs at each frame so first divergence is reported.

**State/code seam evidence:** All machine state is intentionally in the core instance; current declaration includes `frame_number`, `ticks`, CPU, bus and profile (`src/internal.h:68-77`). `[VERIFIED: src/internal.h:68-77]` Quote: “struct nesturbator {” / “uint64_t frame_number;” / “uint64_t ticks;” / “struct nesturbator__cpu cpu;” / “struct nesturbator__bus bus;” / “struct nesturbator__profile profile;”. A movie should carry input, not duplicate emulator state or add host time. Avoid timestamps, native-endian fields, unspecified padding, or third-party format libraries.

## Common Pitfalls

### 1. Header arithmetic or allocation occurs before validation
**What goes wrong:** Malformed or adversarial headers overflow sizes, request unreasonable memory, or allocate before later rejection.  
**How to avoid:** Use checked addition/multiplication for header + trainer + PRG + CHR; compare each section to actual file length and caps before allocator calls; prove the zero-allocation invariant for every rejected fixture. Fuzz corpus replay in all platform legs and libFuzzer nightly.

### 2. Instructions and PPU frames do not share a conserved time cursor
**What goes wrong:** A CPU instruction that crosses the target tick causes frame hashes/replay to depend on call chunking, or repeats/loses CPU cycles on the next frame.  
**How to avoid:** Define exact frame API overshoot contract and carry residual timing, while PPU steps every CPU/PPU relation at the correct order. Add regression where N frames in one call equals the same sequence of N single-frame calls with scripted inputs and identical hashes.

### 3. First frames are hashed before game initialization settles
**What goes wrong:** A title can show transient initialization, vblank races or uninitialized framebuffer content, making baselines flaky or uninformative.  
**How to avoid:** Pick one fixture and deterministic input script for RetroArch screenshot at a frame with stable visible content; explicitly initialize every output pixel each frame; use exact runner frame as screenshot oracle. Store expected hashes for additional frame milestones rather than assuming screenshot implies long-run correctness.

### 4. Palette conversion contaminates emulation identity
**What goes wrong:** Display palette data varies or changes frame hash despite identical emulation.  
**How to avoid:** Hash native pixel values with explicit byte order; run palette regeneration byte-compare independently; compare screenshot only after the known host palette conversion.

### 5. Controller/movie discrepancies are hidden by title-screen automation
**What goes wrong:** A frame hash proves only the input sequence used and may not exercise serial controller reads, both ports, or movie malformed-input paths.  
**How to avoid:** Unit-test the controller protocol; run a fixed scripted input against DABG on both ports and compare runner movie and libretro seam frames. Save command and output evidence.

### 6. AccuracyCoin page results parsed without state discipline
**What goes wrong:** Result RAM is read before the menu/test finishes, a held Start starts a new test, or `$00` not-run / `$FF` skip is counted as pass.  
**How to avoid:** Use pinned ROM-resident page/test directory, deterministic Start pulse with release, bounded frame timeout, and compare result status bytes against a committed scoreboard. This suite is specifically described as writing result bytes to RAM, with its menu/test protocol and pass/fail encodings documented in the preparation reference. `[CITED: .planning/preparation/CONFORMANCE.md, “AccuracyCoin in detail”]`

### 7. RetroArch binary/screenshot step silently skips in required CI
**What goes wrong:** Existing local skip semantics leak into CI and missing binary/screenshot reports success.  
**How to avoid:** Keep current local `ctest -L retroarch` skip when unavailable, but have the separate required macOS workflow install the exact released binary, verify checksum, run with isolated config/content, demand a nonempty screenshot, and fail closed on every missing step. GitHub currently documents standard arm64 `macos-15`; it is a viable runner candidate, but compatibility of the exact RetroArch build and screenshot flags must be proven by the job itself. `[CITED: https://docs.github.com/en/actions/reference/runners/github-hosted-runners]`

Security work still matters at native-code boundaries: treat ROM and movie files as hostile bytes, check every addition/multiplication and allocation bound, avoid indexing from untrusted counts, and fuzz parse plus teardown paths under ASan/UBSan. Preserve the owned-code and clean-room constraints. No security claim depends on a new external service or package.

| Threat | Class | Standard mitigation |
|--------|-------|---------------------|
| Header-size overflow, allocation exhaustion | Memory safety / DoS | Checked arithmetic; file-bound and project caps before allocation; counting allocator assertions; fuzzing. |
| Malformed movie length/index | Memory safety / DoS | Validate framing/length/count and all masks before replay; reject trailing/truncated bytes clearly. |
| ROM-derived invalid mapper/RAM geometry | Faulty mapping / out-of-bounds | Narrow mapper 0 accepted shape; tests at geometry boundaries; no cartridge alloc until validation passes. |
| Untrusted downloaded CI frontend | Supply chain | Pin exact official release, verify SHA-256, do not execute arbitrary latest artifact, keep tokens/permissions minimal. |

## Planning Resolutions and Empirical Gates

1. **RetroArch release and hosted runner (D-08):** No release asset, checksum or hosted compatibility has been proven in this research pass. Plan 03-08 selects an official versioned macOS release asset, records its publisher-provided URL and locally measured SHA-256, and tries `macos-15` arm64 first, then `macos-15-intel` if the asset architecture requires it or the first launch fails. Each candidate must pass checksum verification before execution, report its exact RetroArch version, load the pinned game/core under isolated config, produce a nonempty screenshot, and match the runner's converted pixels on the same game/frame. The trial ends after these two documented runner candidates; a passing combination becomes the committed version/URL/SHA/runner pin and a required `ci-required` dependency. If neither passes, Plan 03-08 remains blocked with the failure logs and no release compatibility claim or skipped CI gate. The pin is revalidated in the required hosted job on each PR. This bounded trial resolves the planning choice without inventing its empirical outcome.
2. **JAM and frame overshoot:** Use a stable, nonzero JAM stop result; the jammed instance remains latched and repeated frame/movie calls cannot advance it. Retain CPU-cycle/PPU-dot overshoot in instance state and deliver each completed frame once. Plan 03-01 tests and documents both boundaries before later movie wiring.
3. **NES 2.0 fixture coverage:** Keep all three pinned game artifacts byte-identical to their upstream builds. Plan 03-02 exercises both iNES and NES 2.0 with synthetic in-memory header/payload cases even if the pinned games all use legacy headers; it validates the actual pinned headers separately.
