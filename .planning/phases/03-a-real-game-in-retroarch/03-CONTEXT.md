# Phase 03: A real game in RetroArch - Context

**Gathered:** 2026-10-08
**Status:** Ready for planning

<domain>
## Phase Boundary

Deliver the first playable cartridge path for NTSC NROM mapper 0: safe iNES/NES 2.0 loading, CPU/PPU integration that renders real game frames, standard controller input on both ports, deterministic frame hashes, and movie replay in the runner and libretro host. Verify the visible RetroArch path with a real open-license game. Run AccuracyCoin pages 2 and 17 and retain the existing six-platform build and hash checks. Requirements: GAME-01 through GAME-06.

This phase does not implement audio (Phase 4), other mappers, PAL/Dendy hardware, expansion controllers, save states, or a palette/options UI. A physical controller is optional for informal play; no behavior covered by the scripted checks requires owner UAT.

</domain>

<decisions>
## Implementation Decisions

### Cartridge fixtures and loader boundary
- **D-01:** Support mapper 0 in iNES and NES 2.0 formats only. Reject malformed, truncated, unsupported, or oversized images with a stable nonzero runner result before allocating cartridge state. Keep the existing counting-allocator and fuzz-regression requirements.
- **D-02:** Use three pinned, redistributable NROM games for complementary coverage: Nesteroids (MIT, upstream commit `ae65d78048af68f3e735c49d77a7f37e976a7afe`), Double Action Blaster Guys (zlib, upstream commit `5ecc60b6af3f726851bfeb1c2555388c5953e0c0`), and RHDE: Furniture Fight (all-permissive, tag `v0.07`, commit `71b18aeb54fefa16373cb3ad2996a2aff90181b5`). DABG adds a two-player case and RHDE exercises CHR RAM. Add each exact ROM artifact to `tests/roms/manifest.txt` with its source, pin, license, and SHA-256; do not commit any unlisted ROM bytes. The former DABG `v2` commit was rejected after its exact `LICENSE.txt` proved GPL-3.0; the replacement commit's exact `LICENSE.txt` identifies the zlib License.

### Rendering and palette
- **D-03:** Close Phase 1's deferred palette work with one documented NTSC-to-sRGB calibration generated by the existing offline palette tool. Keep the core's native pixel values as the canonical frame-hash input, so display calibration does not change emulation hashes. Keep generation reproducible, the runtime core integer-only, and the dependency tree flat; do not add per-game palettes, filters, or a palette-settings UI in this phase.
- **D-04:** Treat rendered output as an integrated PPU result with documented dot/frame timing, register and memory behavior, vblank/NMI, background and sprite paths. Use the hardware references and tests to settle details during research; this discussion does not prescribe internal PPU structures.

### Controller and replay behavior
- **D-05:** Implement the two standard NES controller ports with deterministic per-frame button state. The libretro adapter reads the host's standard joypad interface; the runner and tests inject scripted input. Do not add expansion devices or depend on a physical DualSense or other controller for CI.
- **D-06:** `nesturbator-run --movie FILE` replays controller input and produces the same per-frame hashes on repeated runs. Use an owned, documented format without a new dependency. Exact serialization and error behavior are planning decisions, provided input is deterministic and malformed movies fail clearly.

### Verification and CI
- **D-07:** Make all machine-verifiable success criteria automatic. Run ROM frame hashes, movie replay, malformed-image tests, fuzz corpus replay, AccuracyCoin scoreboard checks, and libretro input/frame seam tests through the normal CI workflow on all six existing platform/architecture legs where applicable. Run libFuzzer in the established Linux nightly lane.
- **D-08:** Make one macOS GitHub Actions job a required RetroArch end-to-end gate. Install a released RetroArch binary at a pinned version and verify its SHA-256; load a pinned game with a controlled config and compare the captured frame against the runner. Missing RetroArch or a missing screenshot fails this CI job. Keep the current local skip behavior for developers who do not have RetroArch installed.
- **D-09:** Run AccuracyCoin pages 2 and 17, read results from emulated RAM, and compare against a committed scoreboard that fails if a passing result regresses. Record command, commit/run ID, and evidence in phase verification; do not ask the owner to repeat command-verifiable checks.

### Dependency and workflow preferences
- **D-10:** Prefer a few owned lines or existing platform/build tools over a new dependency. No emulator source dependency, graphics library, input library, movie-format package, or third-party CI action is needed for this phase.
- **D-11:** Apply the settled automation-first GSD preference: integration, smoke, end-to-end, and seam checks go into CI when they catch recurring regressions; one-time hosted results use read-only evidence collection. Keep owner hand-off only for identity-bound consent or a genuinely subjective judgment that automation cannot establish.

### Phase 2 carry-forward checks for research
- Confirm the selected ROMs do not expose a machine-profile mismatch around the unstable LXA constant (`$EE`).
- Define how the runner/API reports a JAM opcode without making frame execution or movie replay ambiguous.
- Nail down deterministic CPU/PPU frame-boundary behavior when an instruction crosses the requested frame tick.

### the agent's Discretion
- Exact module boundaries and internal PPU representation, based on the established small-C-module style.
- Movie byte layout, versioning, and command-line error text, as long as replay is deterministic and documented.
- Which of the pinned games supplies the mandatory RetroArch screenshot, chosen for a stable early frame and useful visible rendering.
- CI caching details for the version- and checksum-pinned RetroArch release, if they preserve a required fail-closed test.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `src/cpu.c`, `src/bus.c`, `src/frame.c`, and `src/instance.c` — CPU and frame execution to integrate with new PPU and cartridge modules.
- `src/palette.c`, `src/palette_ntsc.c`, and `tools/palgen/palgen.c` — native pixel conversion and the offline generated palette; use these to make the calibration reproducible.
- `runner/main.c` — existing CLI to extend with cartridge loading and `--movie` replay.
- `libretro/libretro.c` and `libretro/nesturbator_libretro.info` — existing host adapter and metadata.
- `tests/libretro/libretro_host.c` — headless host seam for validating input and frame delivery.
- `tests/retroarch/run_retroarch.cmake`, `test.cfg.in`, and `compare_frame.c` — isolated unattended launch, screenshot capture, and exact runner comparison.
- `tests/roms/manifest.txt` and `scripts/hygiene.sh` — existing binary allow-list and repository hygiene enforcement.

### Established Patterns
- Core code is integer-only and uses fixed-width values; generated display data stays outside emulation state.
- CTest uses plain C executables, explicit fixtures, exact output checks, and source/hash policy scripts.
- ROM sources and binaries are pinned, checksummed, and reviewed as licensed test fixtures; third-party emulator source is never used.

### Integration Points
- Cartridge load/unload joins the public API, runner content path, and libretro `retro_load_game` lifecycle.
- PPU memory/register access joins the existing CPU bus and machine clock; controller reads join the CPU I/O bus and the libretro host input callbacks.
- Deterministic frame output must agree through the runner, the libretro test host, and RetroArch screenshot path.
</code_context>

<specifics>
## Specific Ideas

- A user can optionally try the core with their Bluetooth DualSense through RetroArch, but controller hardware is never a test prerequisite.
- CI should catch every recurring, machine-verifiable regression so phase completion does not depend on the owner repeating manual gameplay or screenshot checks.
- Keep the existing `cmake --workflow --preset ci` contract and test only the RetroArch release binary, not its source.
</specifics>

<deferred>
## Deferred Ideas

- APU/audio synthesis and audio hashes belong to Phase 4.
- Mappers other than NROM, PAL/Dendy profiles, expansion controllers, save states, and battery RAM remain outside Phase 3.
- Per-game/user-selectable palettes, filters, and other presentation settings are deferred; preserve the single deterministic default calibration.
- The Phase 2 carry-forward checks above are research gates, not permission to expand Phase 3 beyond the roadmap requirements.
</deferred>
