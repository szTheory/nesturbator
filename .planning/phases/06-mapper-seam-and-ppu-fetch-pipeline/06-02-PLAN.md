## Decisions taken under Claude's discretion and orchestrator directions

- **Shifter polarity (direction 2):** the low pattern plane shifts in 0 and the high plane shifts in 1 (NESdev "PPU rendering": "1 for the high bitplane and 0 for the low bitplane"). This corrects D-10's "feeding in 1" for the low plane only.
- **Dot-0 bus value (direction 3):** modelled. On the wrap into dot 0 of a rendering line, the bus shows the BG-lo address of the pending tile: `((control & 0x10) << 8) | (bg_nt << 4) | ((v >> 12) & 7)`. Hash-neutral.
- **`$2007` during rendering (direction 4, Discretion):** included, in the pipeline commit, before re-pinning.
- **Odd-frame dummy read (direction 5):** D-10's choice kept: the skip after dot 339 lands on (0,0) without the dot-340 read, so the bus keeps the dot-339 NT address. Recorded assumption: the NESdev wiki describes the last dummy fetch's tick replacing the idle tick at (0,0), which would add one NT read a mapper could see. The dropped read itself is hash-neutral and A12-neutral (an NT address has A12 = 0). It is not A12-neutral overall: with PPUCTRL bit 4 set, an even frame logs an A12 rise at line 0 dot 0 (the dot-0 BG-lo address) while an odd frame does not, so its first rise on line 0 is at dot 5. That matches the wiki reading too (an NT tick, not the BG-lo address, occupies (0,0) on odd frames). `ppu.fetch` asserts the odd frame's edge log, and this is recorded as a **Phase 9 input**: MMC3's filter sees one fewer rise per odd frame with BG at `$1000`.
- **D-13 trace hook dropped (direction 6):** every D-13 assertion is kept, but tests observe by single-stepping `nesturbator__ppu_run_until(nes, nes->ppu.ppu_ticks + 8u)` and reading `ppu.bus_addr`, `ppu.v`, `ppu.scanline`, `ppu.dot`, plus the test board's A12 edge log. No production code is added for tracing ("remove the need").
- **OAMADDR forced to 0 during 257-320 (direction 7): deferred, not dropped.** NESdev "PPU registers" (OAMADDR) documents the PPU setting OAMADDR to 0 on each tick of dots 257-320 of the pre-render and visible lines. It is not part of MAP-02 (it moves no fetch address and no A12 edge) and no locked decision asks for it. It is deferred to a later PPU accuracy phase, to be added when an AccuracyCoin OAM test is traced to it; Task 3 records it under "Deferred" in `06-02-SUMMARY.md` so it reaches the phase verification and the backlog.
- **Commit shape (explicit exception to a green test set at every commit, CLAUDE.md rule 6):** Tasks 1 and 2 change frame output, so `runner.write_hashes.content` is red at their commits until Task 3's single re-pin. This is by design: D-17 locks one revision bump and one re-pin, in one commit, after the pipeline is complete. Their verify commands therefore run `ctest -R` subsets plus the protected AccuracyCoin pages. The exception is the same as in Plan 01: intermediate task commits on the phase branch may be red and reach the remote only as ancestors; nothing of this plan is pushed before Task 3, whose pushed branch tip passes the full `cmake --workflow --preset ci` locally and the PR's CI run; the PR is squash-merged, so `main` only ever receives one green commit. Rule 6 is met at the merge, and each behaviour change still lands with its test and README sentence in the same commit.
- **Read-dot address (D-10):** each read dot recomputes the full address with the same formula as its paired address dot, on live state, and drives `set_bus((formula & 0x3F00) | ale_latch)`. One helper per access kind computes the formula, so the address dot and the read dot cannot diverge: NT `0x2000 | (v & 0x0FFF)`; AT `0x23C0 | (v & 0x0C00) | ((v >> 4) & 0x38) | ((v >> 2) & 0x07)`; BG-lo `((control & 0x10) << 8) | (bg_nt << 4) | ((v >> 12) & 7)` and BG-hi that plus 8, whose bits 8-13 are PPUCTRL bit 4 at bit 12 and `bg_nt`'s high nibble at bits 8-11 (never v's fine Y); sprites, the slot's pattern formula. With nothing changed since the address dot, the read dot drives the same address and A12 does not toggle; a PPUCTRL bit 4 write between the two (RHDE's mid-line `$2000` writes) moves A12 on the read dot, as the live high bits do on hardware.
- **D-15 correction:** CONTEXT D-15 says "the 512×240 plane"; four nametables with vertical mirroring form a 512×480 plane (Y in 0-479), so the sampler and the segment tables use 512×480. Same intent, corrected size.
- **README per commit (CLAUDE.md rule 6):** Task 1 writes the README sentences for the behaviour it lands (background from v, scroll at the copies, `$2007` while rendering, the PPU bus and A12 reported to the board, and the mapper-interface sentence moved from Plan 01); Task 2 writes the sprite per-slot sentence and the mid-frame-scroll status sentence; Task 3 changes only the revision wording.

Tasks are tightened instead: the performance baseline moved to Plan 01 Task 3, README work is spread so no task carries all of it, and Task 3 is bookkeeping plus gates. The overrun is accepted.
